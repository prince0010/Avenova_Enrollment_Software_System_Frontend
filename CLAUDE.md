# Enrollment System — Frontend

## What this is

The client for the enrollment system backend (see `../backend/CLAUDE.md`), delivered as a **desktop app**: a Next.js (App Router) + TypeScript + Tailwind CSS + shadcn/ui web app wrapped in an **Electron** shell. The system is "system software," not a public website — users launch a desktop window, not a browser tab. The same app still works in a plain browser during development. It talks to the backend exclusively over its HTTP API at `NEXT_PUBLIC_API_URL` — it does not (and should not) talk to Prisma or Redis directly; those are backend-internal.

Columns: student, school year, enrolled date, consent count (`X/4`), View action (`components/enrollment-view-dialog.tsx`, scoped to a single period's consents). No search/filters/mutations yet (PATCH/DELETE on an individual period record isn't built on the backend either) — otherwise pattern-matches Archive's read-only-list-plus-pagination shape. `listEnrollments()` filters to `CONFIRMED` server-side, so this page needed no changes when the pending/confirm/reject workflow was added.
- `/dashboard/fees` ("Fees" in the sidebar, `Receipt` icon) — manages the global fee catalog (`GET/POST/PATCH/DELETE /api/fees` + `GET /api/fees/:id/history`; see `backend/CLAUDE.md`'s "Fees" section for the versioning/snapshot model): a table of fee items (name, PHP amount via `formatPeso` in `lib/format.ts` — amounts arrive as **strings**, Prisma Decimal serialization), an Add/Edit dialog (one dialog, `editing` state decides which; client-side checks for non-empty name and amount > 0; 409 duplicate-name errors surface in the dialog), a per-fee **History** dialog (the `FeeVersion` audit trail, newest first, current marked), a Delete confirm dialog (backend gate is ADMIN-only), and a "Total per enrolled student" line. **Adds charge current students too; updates affect future enrollments only; deletes propagate everywhere**: each enrollment freezes an `EnrollmentFee` snapshot at confirmation, so the student View dialog's "Fees (as of enrollment)" section reads `student.latestEnrollment.fees` (shipped with the student record — no separate fetch), never the live catalog. Creating a fee also appends it to every currently-enrolled student's latest confirmed enrollment; updating a fee never rewrites an already-enrolled student's record; *deleting* a fee removes it from every student's snapshot and totals (explicit product decisions; the add/edit/delete dialogs each state their rule). No per-student assignment/overrides, no payments/balances tracking yet.
- `/dashboard/archive` — soft-deleted students (`GET /api/students/archived`) with View and Restore (confirm dialog → `POST /api/students/:id/restore` → back to Students). Pagination shares `components/table-pagination.tsx` with Students; "Enrolled" column shares `components/enrolled-cell.tsx` with Students.
- **App shell** (`app/dashboard/layout.tsx`): left sidebar (`components/app-sidebar.tsx`) + top bar with the user's name and an avatar-initials dropdown (`components/user-menu.tsx` — View profile dialog, Edit profile dialog wired to `PATCH /api/users/me`, Log out).

- **Table loading state**: Students, Pending, Enrolled, and Archive all show a skeleton (`components/table-skeleton.tsx`'s `TableSkeletonBody`, shadcn `Skeleton`) inside the real table header while their `GET` call is in flight, instead of a plain "Loading..." string — shimmering rows of varied width, no layout jump when real data arrives. Reusable for any future table via its `columns` prop.
- `/` — redirects straight to `/dashboard` (which itself bounces to `/login` if not authenticated).

Chart styling follows the dataviz conventions: single series in blue (`#2a78d6` light / `#3987e5` dark via the shadcn chart `theme` config), bars capped at 24px with 4px rounded tops, no legend (single series — the title names it), recharts tooltip for hover with a muted cursor rectangle. ## How to run it

1. Backend must be running first: `docker compose up -d && npm run dev` in `backend/` (see `backend/CLAUDE.md`).
2. Backend's `.env` `CORS_ORIGIN` must exactly match this app's dev URL (protocol + host + port) — the backend's CORS middleware takes a single origin string, not a list, and `credentials: true` is set so wildcards won't work either. Restart the backend after changing it (env is read once at boot).
3. `npm run electron:dev` here — starts `next dev` on `http://localhost:3000` and opens the Electron desktop window once it's ready (via `concurrently` + `wait-on`). Plain `npm run dev` still works for browser-only development. (Next auto-increments to 3001, etc. if 3000 is busy; if so, update `CORS_ORIGIN` to match — and note `electron/main.js` defaults to loading 3000, overridable via `ELECTRON_START_URL`.)
4. Log in with the seeded admin: `admin@example.com` / `ChangeMe123!` (from `backend/prisma/seed.ts`).

## Electron shell

- `electron/main.js` — the whole main process: one `BrowserWindow` (1280×800, `contextIsolation: true`, `nodeIntegration: false`) that loads `ELECTRON_START_URL` (default `http://localhost:3000`) in dev. `package.json` has `"main": "electron/main.js"` so `electron .` works.
- `electron/preload.js` — intentionally empty; the renderer is the Next.js app and needs no Node/Electron APIs yet. Add `contextBridge.exposeInMainWorld` calls there if a future feature needs native access.
- The shell is deliberately thin: all auth/routing/UI logic lives in the Next.js app, so everything keeps working identically in a plain browser. Cookies (the httpOnly refresh token) work the same in Electron's Chromium as in a browser — no auth changes were needed.

## Packaging (Windows `.exe`)

`npm run electron:build` (`next build && electron-builder --win nsis`) produces a real installer at `frontend/release/Avenova Enrollment System Setup <version>.exe` (NSIS, `oneClick: false` so it shows the install-location picker + a desktop shortcut option). Built and verified end-to-end (installer launches, logs in against the real backend, dashboard loads).

- **Static export, not a bundled Node server.** `next.config.ts` has `output: "export"` + `images.unoptimized: true` — `next build` writes plain HTML/CSS/JS to `out/` instead of a server build. This works because every page here is already client-rendered and talks to the backend over HTTP (no route handlers, no `"use server"`, no dynamic `[id]` routes, no `middleware.ts` — confirmed absent before choosing this over bundling a Next server binary). Simpler and more robust than shipping `next start` inside Electron. **This means `npm run start` (`next start`) no longer works** now that the build is export-only — it was never part of the Electron path, but if plain-browser production hosting is needed again, serve `out/` directly (e.g. `npx serve out`) instead.
- **`electron/main.js` runs a tiny bundled static server in packaged mode** (`app.isPackaged`), not `loadFile`/`file://` — `out/`'s pages reference absolute `/_next/...` paths, which break under `file://` and hit Chromium's CORS restrictions on that protocol. `startStaticServer()` spins up a local-only `http` server backed by `serve-handler`, serving `out/` (shipped as an `extraResources` entry, so it lands in `resources/out` outside the asar — read via `process.resourcesPath`, not `__dirname`).
- **Fixed port (`PACKAGED_APP_PORT = 51247` in `main.js`), not OS-assigned** — the backend's `CORS_ORIGIN` is a single exact-match string (see `backend/CLAUDE.md`), so the packaged app needs one stable, known origin to allow. Set the backend's `.env` `CORS_ORIGIN=http://localhost:51247` to test the packaged build; swap back to `http://localhost:3000` for `electron:dev`/`next dev` afterward (same single-origin gotcha as "How to run it" above — restart the backend after changing it).
- **Navigates to `http://localhost:51247`, never `http://127.0.0.1:51247`**, even though the static server's socket binds to `127.0.0.1` — the backend's refresh-token cookie is `Domain=localhost` (`COOKIE_DOMAIN` env), which won't round-trip against a bare IP origin (same gotcha as the "Gotchas" section below, now applies to the packaged app too). Verified live: a real prior dev-mode login's cookie (`Domain=localhost` ignores port) round-tripped successfully into the freshly packaged app, confirming both the CORS origin and cookie domain line up.
- **`app.requestSingleInstanceLock()`** — without it, launching the packaged app twice would race two processes for the same fixed port instead of just focusing the existing window.
- **Icon**: `build/icon.ico`, generated once from `public/images/Avenova_logo.png` via `png-to-ico` (`png-to-ico`'s CJS export is under `.default`, not the module root — see the one-off generation command in git history if regenerating after a logo change). Referenced via `build.win.icon` in `package.json`; the `BrowserWindow`'s own runtime/taskbar icon (`electron/main.js`) still just uses the source `.png` directly, which Electron accepts fine cross-platform.
- **electron-builder config lives in `package.json`'s `"build"` key** (not a separate `electron-builder.yml`) — `appId: com.avenova.enrollment-system`, `productName: "Avenova Enrollment System"`, output to `release/`, `out/` shipped via `extraResources` as noted above.
- **Known gotcha**: the packaged app's Electron `userData` folder (hence its cookie/session storage) is named `frontend` — Electron derives it from package.json's `"name"` field, not `"productName"`, and nothing in `main.js` calls `app.setName()` to override it. This means the packaged app and `npm run electron:dev` currently **share the same persistent login session** on a given machine. Harmless for single-developer use; call `app.setName("Avenova Enrollment System")` before `app.whenReady()` if dev/packaged sessions ever need to be isolated.
- **Not signed** — `electron-builder`'s NSIS step invokes `signtool.exe` but there's no code-signing certificate configured, so Windows SmartScreen will likely flag the installer as from an "unknown publisher" until one is added.
- **Not built yet**: auto-update, a portable (installer-less) build variant, macOS/Linux targets, CI-driven builds — this was packaged and verified locally only.

## Auth model as implemented here

- **Access token lives in memory only** (`lib/api-client.ts`, module-level variable) — never `localStorage`/`sessionStorage`. This matches the backend's own security posture: enrollment data downstream includes medical/behavioral/custody info, so the client deliberately avoids giving an XSS payload a durable place to read a live token from.
- **Refresh token is opaque to the frontend** — it's an httpOnly cookie the backend sets/reads; the frontend only ever knows it exists implicitly (a successful `POST /api/auth/refresh` means it was valid).
- **Hydration on mount** (`lib/auth-context.tsx`): since the access token is never persisted, every hard refresh starts from zero — `AuthProvider` calls `POST /api/auth/refresh` (cookie sent automatically), then `GET /api/users/me` with the resulting token, to rebuild `{ user }` state. Until that resolves, `isLoading` is `true` and route guards show a loading state rather than prematurely redirecting.
- **Transparent refresh-on-401** (`lib/api-client.ts`): any authenticated call that 401s (access token expired after its 15m lifetime) triggers one `POST /api/auth/refresh` attempt (de-duped across concurrent callers via a shared in-flight promise), then retries the original call once. If refresh also fails, a registered `onForceLogout` callback clears the auth context's `user` state — the next guarded route render redirects to `/login`.
- **Route guards are client-side only** (`components/auth-guard.tsx`), no `middleware.ts`. A Next.js edge middleware can only see cookies, and the only cookie present is the httpOnly refresh cookie — it can tell "cookie present" from "cookie absent" but not "valid" from "expired/revoked," so the client would need its own real check regardless. Keeping one mechanism (client-side, backed by `useAuth()`) avoids two subtly different sources of truth about whether a session is actually live.
- The shadcn `form` registry component (react-hook-form + zod resolver wrapper) resolved to an empty stub under the currently-installed `shadcn` CLI/`base-nova` style — the login form is hand-rolled with plain `useState` + a zod `safeParse` on submit instead of pulling that dependency in. Fine for a two-field form; revisit if a form gets meaningfully more complex.
- This shadcn style is built on **Base UI** (`@base-ui/react`), not Radix — component internals differ from classic shadcn. Known difference hit already: `DropdownMenuLabel` throws "MenuGroupContext is missing" unless wrapped in `DropdownMenuGroup`.

## Env vars

- `NEXT_PUBLIC_API_URL` — base URL of the backend API, including the `/api` prefix (e.g. `http://localhost:4001/api`). Public (`NEXT_PUBLIC_`) because the API client runs in the browser. See `.env.local.example`.

## Gotchas

- **CORS_ORIGIN is single-origin and exact-match** — protocol, host, and port all have to match the frontend's actual dev URL exactly, or every request will fail CORS silently (browser console, not a clean error in the UI).
- **Cookie domain is `localhost`-scoped** (backend's `COOKIE_DOMAIN` default) — always access the frontend via `http://localhost:PORT`, never `http://127.0.0.1:PORT`, or the refresh cookie won't round-trip and auth will silently break.
- Access token expires in 15 minutes; if you're poking around manually and things suddenly start 401ing, that's expected — the transparent refresh should handle it invisibly during normal use.
- This is Next.js 16 (see `AGENTS.md` at this folder's root for framework-specific agent notes) — check `node_modules/next/dist/docs/` before assuming an older Next.js pattern still applies.
- **Don't run two `next dev` instances at once.** If port 3000 is already taken, a second `next dev` (or `electron:dev`) silently moves to 3001 — but Electron's default URL and the backend's `CORS_ORIGIN` are both pinned to 3000, so you'd be looking at a stale window while editing a server nobody's talking to. If the app ever shows old content after a change, check for a leftover dev server on 3000 first.
- **Adding a brand-new route folder can 404 under a stale `.next` cache** — hit once after adding `app/dashboard/enrollments/`: the dev server (already running from before the new folder existed) served a genuine 404 for the new route even after the file was in place, logging `Compiling /_not-found/page` instead of the new route. Fix: stop the dev server, `rm -rf .next`, restart. Existing routes being edited don't need this; it's specifically new route folders added while a dev server is already running.
- **`Button render={<Link .../>}` needs `nativeButton={false}`** — Base UI's `Button` primitive defaults to assuming its `render` target behaves like a native `<button>`; rendering a `<Link>` (an `<a>`) without also setting `nativeButton={false}` throws a dev-console warning ("A component that acts as a button expected a native `<button>`...") and shows up as a Next.js dev-overlay issue badge. Anywhere a `Button` wraps a `Link` for navigation (see the "Add student" button on `/dashboard/students`), set `nativeButton={false}`.
- **Zod field errors show the generic "expected string, received undefined" instead of a custom `.min()` message if the field starts as `undefined`** — `z.string().min(1, "custom message")` only reaches the custom message once the value is type-valid (a string); an `undefined` initial value fails the base type check first, before `.min()` ever runs. Any hand-rolled form state must initialize every validated field to its empty value (`""` for text, `false` for checkboxes) up front, not leave keys absent until the user types — see `components/student-create/steps-config.ts`'s `buildInitialValues()`.
